# AI 动态生成问卷的踩坑全记录：从"能跑就行"到生产级稳定

> 这不是一篇"五分钟搭建 AI 问答系统"的速成教程，而是一份真实还原：从 Supabase 初始化时机，到 LLM 流式输出的 JSON 截断与解析，再到"题目生成一半卡住了"的前端体验地狱，以及最终如何用两阶段大纲 + 兜底 + 心跳机制逐一填坑的完整记录。

---

## 🎯 核心主题：AI 问卷生成器的六连坑，与那套"永远不让用户看到空白报错"的容错体系

### 🟢 S (Situation) - 稳定的前度平衡

> *用 2-3 句话交代原本平稳、大家都习以为常的现状。*

项目是一个"人类核心能力金字塔"测评系统——5 个能力维度，每个维度需要 10 道精心设计的情境题。最开始用的是题库固定方案：预设 25 道题，用 Recharts 渲染结果。简单、可靠、从不报错。

代码跑了小半年，集群稳如老狗，用户填问卷的体验丝滑流畅。团队都觉得这套架构够用了，直到产品经理提了一个新需求：**能不能让 AI 动态生成题目，每次问卷都不一样？**

于是引入 DeepSeek `deepseek-v4-pro` 模型：用户输入自己的 API Key，前端实时调用模型生成题目，回答完成后，再用 AI 生成个性化报告。

这个改动，引出了一连串意想不到的坑。

- **事实陈述**：静态题库方案稳定运行半年，无一例生产故障；但题目不可扩展，每次调整题目都要改代码
- **心智共鸣**："当时我们也是这样——用固定题库，简单粗暴，但后来发现题目没法个性化"

---

### 🔴 C (Complication) - 平衡的剧烈打破

> *用 2-3 句话撕开痛苦的口子，描述突然发生的变量或致命痛点。*

引入 AI 的第一天，第一个坑就炸了：`npm run build` 直接报错——环境变量 `undefined`。

紧接着是 JSON 截断：DeepSeek 返回几千 token 的 JSON 数组，模型有时在生成一半时被截断，JSON 根本无法解析，整个请求白跑。增大 `max_tokens`？治标不治本。调 `temperature`？收效甚微。

JSON 好不容易返回了，又被 markdown 代码块包裹、嵌套层级错乱、字段名大小写不一致——模型输出 `"optionA"` 而不是 `"A"`，解析代码直接崩溃。

好不容易 JSON 解析通了，用户看到的却是一片空白——生成 10 道题需要 1 次大纲 + 10 次单题调用，总耗时 30-60 秒，没有任何进度反馈，用户以为页面卡死了，直接关掉。

- **冲突爆发**：
  - 环境变量在模块加载时就炸了（`process.env` 尚未注入）
  - JSON 被截断、格式混乱、解析失败，三连击
  - 题目生成"卡住了"，前端体验一片空白
- **次生灾害**（如不解决会怎样）：
  - 用户流失：30 秒无反馈直接关闭页面
  - 报告生成失败：用户答完题后看到的是空白——最无法接受的时刻
  - 整个功能从"AI 加持"变成"AI 挖坑"

### 🔵 Q (Question) - 悬而未决的致命一问

> *精炼成一句话，直击技术核心，勾起读者的探索欲。*

- **核心追问**：LLM 的输出从不可靠到不可控——从环境变量、JSON 截断、解析失败、到用户等待无反馈，每一个环节都可能崩溃，如何在每个环节都建立容错机制，让整个系统"任意单点失败时优雅降级，而不是整体崩溃"？

---

### 🟣 A (Answer) - 最终的破局解法

> *亮出最终架构或技术方案，证明它是当下最优解。*

#### 破局技术栈 / 架构

**坑一解法：惰性初始化 + demo 降级**

```javascript
// ❌ 模块加载时执行，此时 process.env 尚未准备好
const supabase = createClient(process.env.NEXT_PUBLIC_SUPABASE_URL, ...);

// ✅ 用函数包装，首次调用时再初始化
function getSupabaseClient() {
  const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL;
  const supabaseKey = process.env.NEXT_PUBLIC_SUPABASE_KEY;
  if (!supabaseUrl || !supabaseKey) {
    return null; // 优雅降级，不崩溃
  }
  return createClient(supabaseUrl, supabaseKey);
}
```

**坑二解法：两阶段生成（大纲 + 单题并行）**

```
Phase 1: 模型生成 10 个大纲（JSON 数组，只有几百 token）
         ↓ 如果截断 → 发送 continue 请求补全
Phase 2: 并行生成每道题（Promise.allSettled）
         ↓ 每题最多重试 3 次
         ↓ 重试耗尽 → 兜底生成（fallback prompt）
```

好处：即使被截断也很容易从已输出内容中提取有效 JSON 片段；Phase 2 每题独立，8/10 题成功也比全失败强。

**坑三解法：三层降级解析 + 字段名归一化**

```javascript
// 第一层：直接解析（json_object 模式下最干净）
try { question = JSON.parse(qContent); } catch {}

// 第二层：从字符串中提取 JSON 对象
if (!question) {
  const jsonMatch = qContent.match(/\{[\s\S]*\}/);
  if (jsonMatch) { try { question = JSON.parse(jsonMatch[0]); } catch {} }
}

// 第三层：清理 markdown 包裹
if (!question) {
  const cleaned = qContent
    .replace(/^```(?:json)?\s*/i, '').replace(/\s*```$/i, '').trim();
  try { question = JSON.parse(cleaned); } catch {}
}

// 字段名归一化
if (question.optionA && !question.options?.A) {
  question.options = { A: question.optionA, B: question.optionB, C: question.optionC };
}
```

**坑四解法：SSE 流式输出 + 心跳机制**

后端使用 Server-Sent Events 逐事件推送，前端维护完整状态机。对于"卡住"检测：每收到任意事件就更新 `lastActivityTime`，前端每 10 秒检查一次，超过 30 秒无活动则显示警告——"可能是网络问题，请耐心等待"，并给出重试入口。

```javascript
// 心跳检测：超过30秒无活动则显示警告
const interval = setInterval(() => {
  const elapsed = (Date.now() - lastActivityTime) / 1000;
  if (elapsed > 30) {
    setStuckWarning({ layerId, layer });
  }
}, 10000);
```

**坑五解法：批次设计 + 层间顺序、层内并行**

两批次设计：先生成前 2-5 层，用户回答完再看第二批入口。层间顺序生成（避免 API 并发限制），层内并行（快速产出）。用户每 5-10 秒能看到一个新层"亮起来"，有明确的节奏感。

**坑六解法：AI 报告 + fallback 双保险**

```javascript
const localStats = computeLayerStats(questions, answers); // 100% 可靠

let aiReport = null;
try {
  aiReport = await generateAIReport(...);
} catch (err) {
  // 记录错误，不打断流程
}

const fallbackReport = generateFallbackReport(questions, answers, mode);
// 纯统计：A/B/C 选择次数、极端选择率、整体倾向——本身就有价值

return { aiReport, fallbackReport, localStats };
```

#### 收效与亮点数据

| 环节 | 容错机制 | 效果 |
|------|---------|------|
| 环境变量 | 惰性初始化 + demo 模式 | 构建不再崩溃 |
| JSON 截断 | 两阶段大纲 + continue | 截断可恢复 |
| JSON 解析 | 三层降级 + 归一化 | 解析成功率大幅提升 |
| 单题失败 | 每题独立重试 3 次 + fallback | 部分成功可接受 |
| 用户等待 | SSE 流式 + 心跳警告 | 30 秒无活动感知 |
| 报告生成 | AI 报告 + fallback 双保险 | 用户永远看到结果 |

### 📋 总结：AI 动态生成的质量保障体系

踩坑的核心原因其实是同一个：**LLM 的输出是不可靠的，需要在每一个环节都建立容错机制**。

最终系统能够在**任意单个环节失败时优雅降级，而不是整体崩溃**。这才是 AI 应用从 demo 到生产级稳定性的核心差距。
