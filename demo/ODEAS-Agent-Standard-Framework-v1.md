# BeBios Agent 标准框架概念设计

> Ontology Driven Enterprise Agent System — Standard Agent Framework
> 版本：v1.0 | 日期：2026-06-11

---

## 1. 框架定位与核心理念

### 1.1 是什么

BeBios Agent 标准框架是一个**企业级 Chatbot Agent 的分层参考架构**，定义了从用户交互到工具执行的完整技术栈分层、每层职责边界、子模块组成及层间协作关系。它不是某个具体实现，而是一套**可落地、可裁剪、可组合**的设计规范。

### 1.2 解决什么问题

| 痛点 | 框架如何解决 |
|------|-------------|
| Agent 系统各模块职责不清、边界模糊 | 7层+3横切 的严格分层，每层有明确的输入/输出契约 |
| NLU/规划/执行混在一起，难以独立演进 | 语义理解→规划→执行 三层解耦，各自可替换实现 |
| 会话状态散落各处，断点恢复困难 | 统一的上下文状态层，集中管理对话/槽位/HITL状态 |
| 工具调用缺乏可靠性保障 | 执行层内建重试、幂等、熔断、补偿事务 |
| 安全与成本管控后补 | 横切层从 Day 1 覆盖安全、可观测、成本、限流 |
| 多 Agent 协作缺乏规范 | 编排层定义注册/路由/协作/聚合的标准模式 |

### 1.3 设计原则

1. **单向依赖**：上层依赖下层，下层不感知上层。横切层垂直穿透所有业务层。
2. **职责正交**：每层只解决一类问题，不在自己的层做别的层的事。
3. **可裁剪**：MVP 只需 L1+L2+L3+L7，其余按需引入。
4. **协议驱动**：层间通过明确定义的数据结构交互，不依赖具体实现。

## 2. 架构总览

```
┌─────────────────────────────────────────────────────────┐
│                    M1 反思与学习引擎                      │
├─────────────────────────────────────────────────────────┤
│                    M2 安全与治理层                        │
├─────────────────────────────────────────────────────────┤
│                    M3 基础设施横切层                      │
├────┬────┬────┬────┬────┬────┬────┬──────────────────────┤
│ L1 │ L2 │ L3 │ L4 │ L5 │ L6 │ L7 │   (7 层业务栈)       │
└────┴────┴────┴────┴────┴────┴────┴──────────────────────┘
```

- **L1~L7**：纵向业务分层，请求自上而下流转
- **M1~M3**：横向横切关注点，垂直穿透所有业务层

## 3. 各层详细设计

---

### L1 交互呈现层 (Presentation & Interaction Layer)

**定位**：面向终端用户的 UI 框架层，负责所有「看得见、点得着」的交互能力。类似于 chatbot-ui 这类前端框架的标准化抽象。

**解决的核心问题**：不同渠道（Web/企微/钉钉/飞书）的交互体验统一，以及人机协作场景下的审批卡片、文件传输等富交互能力。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **渠道接入网关** | 多协议适配（WebSocket / HTTP / 企微 / 钉钉 / 飞书），消息格式标准化，渠道身份认证 | 一次开发多渠道部署，屏蔽协议差异 |
| **富媒体传输器** | 文本/文件/图片的双向传输，大文件分片与断点续传，媒体格式自适应（按渠道能力降级） | Agent 不仅能聊天，还能收发文件、图片，覆盖实际业务场景 |
| **HITL 交互卡片引擎** | 审批/确认/选择类卡片的声明式渲染，卡片动作回调处理（同意/拒绝/修改），卡片状态实时更新（待审→已审） | 人机协作的核心交互载体——让审批、确认等动作不依赖自然语言歧义 |
| **输出渲染器** | 文本 Markdown 渲染，富媒体卡片构建（表格/图表/列表），语音合成适配（TTS），流式输出（打字机效果） | 统一渲染管线，后端只出结构化数据，前端按渠道能力渲染 |

**关键设计点**：
- L1 不管理会话状态（那是 L3 的职责），只负责呈现与采集
- HITL 卡片是**声明式**的：后端返回卡片 Schema（JSON），前端按渠道能力渲染成按钮/表单/链接
- 富媒体传输器是区分「聊天机器人」和「业务 Agent」的关键——纯文本聊天的 Agent 无法处理合同审批中的附件上传

---

### L2 语义理解层 (Semantic Understanding Layer)

**定位**：将自然语言输入转化为结构化意图+槽位的 NLU 管线。

**解决的核心问题**：用户说的话 → 机器能理解的结构化表示。这是整个系统"听懂人话"的层。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **意图识别器** | 规则匹配（正则/关键词）→ 语义相似度（Embedding）→ LLM 意图解析，三级fallback；置信度评估与低置信度追问触发 | 用户表达千变万化，需要多策略识别意图，且需要知道"自己不确定" |
| **槽位提取器** | 基于规则的槽位抓取（日期/金额/手机号等），基于本体的槽位推断（从实体关系推导隐含槽位），必填槽位校验与缺失追问 | 光知道意图不够，还要提取执行所需参数；缺参数时主动追问 |
| **语义映射引擎** | 同义词库管理，实体别名解析（"那个项目"→具体项目ID），业务术语标准化器（"报销"="费用申请"） | 企业内部术语混乱，同一概念多种说法，需要归一化 |

**关键设计点**：
- L2 不包含本体解析（归L4）和规则校验（归L5），聚焦纯粹的**理解**职责
- 意图识别的三级 fallback 机制：规则最快最准 → Embedding 覆盖泛化 → LLM 兜底但慢
- 槽位提取依赖L4的本体定义做推断，但不自己解析本体

---

### L3 上下文状态层 (Context & State Layer)

**定位**：管理对话过程中所有可变状态的单一真相来源（Single Source of Truth）。

**解决的核心问题**：对话不是无状态的——多轮追问、中途改主意、审批等待、断点恢复，都需要状态管理。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **会话状态管理器** | 全局状态（会话ID/渠道/时间戳），用户级状态（身份/权限/偏好），任务级状态（当前任务类型/进度/关联数据） | 三级状态隔离，不同粒度的状态有不同的生命周期和可见范围 |
| **槽位填充追踪器** | 已填充槽位登记簿，缺失槽位识别器，槽位默认值填充器（基于用户画像/历史偏好） | 多轮对话中追踪"还缺什么参数"，自动补全可推断的参数 |
| **对话状态机** | 状态转换引擎（定义合法转换路径），追问策略生成器（怎么问、问什么），对话流程模板加载器（预定义业务流程） | 不是任意对话都有效，需要引导用户沿业务流程走 |
| **断点恢复器** | 检查点持久化（每次状态变更时快照），状态快照捕获与序列化，断点恢复执行（反序列化+状态重建） | 用户关掉对话再回来，或系统重启，能从断点继续 |
| **HITL 状态同步器** | 等待审批状态标记，审批结果接收，流程恢复触发 | 人机协作中"等审批"这个挂起态的管理 |

**关键设计点**：
- L1 的 Session Lifecycle（创建/销毁）在 L3 统一管理，L1 只持有 Session ID 引用
- 断点恢复要求状态可序列化——所有状态对象必须实现序列化协议
- HITL 状态是 L3 与 L1 协作的桥梁：L3 标记"等待审批"，L1 渲染审批卡片，用户操作后 L1 回调 L3

---

### L4 记忆与知识层 (Memory & Knowledge Layer)

**定位**：系统的长期记忆和领域知识基础设施，提供"知道什么"和"记住什么"的能力。

**解决的核心问题**：Agent 不是每次对话都从零开始——它需要知道业务规则、记住用户偏好、理解领域概念之间的关系。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **知识检索器** | 向量检索（语义相似），关键词检索（BM25精确匹配），混合融合排序（RRF reciprocal rank fusion），多路召回编排器 | 单一检索方式不够：向量找"意思接近的"，关键词找"精确匹配的"，融合取长补短 |
| **本体解析器** | 实体定义加载器（从YAML/JSON Schema加载），关系图构建器（实体间关系建模），业务约束解析器（从本体推导约束规则） | 本体是企业知识的骨架——定义了有哪些实体、它们什么关系、受什么约束 |
| **长期记忆库** | 用户画像存储（偏好/权限/历史摘要），交互历史归档（关键对话片段），偏好学习记录（显式+隐式偏好） | 跨会话的个性化：记住用户上次问过什么、偏好什么格式 |
| **工作记忆管理器** | 当前任务上下文缓存，中间结果暂存器，上下文压缩器（摘要/滑动窗口/token预算分配） | LLM 上下文窗口有限，需要智能选择"塞什么进去" |
| **记忆注入器** | 系统提示构建器，相关知识挂载器（检索结果注入），用户画像注入器 | 把记忆"喂"给LLM的标准方式——不是什么都塞，按相关性选择 |
| **GraphRAG 引擎** | 知识图谱构建器，实体关系推理器，多跳查询执行器 | 文档检索只能找到"提到A的段落"，GraphRAG能回答"A和B通过C有什么关系" |

**关键设计点**：
- 本体解析器从原L2迁入，因为本体是知识定义，不是实时理解管线
- 工作记忆的上下文压缩是企业级Agent的刚需——token贵且窗口有限
- GraphRAG 与向量检索互补：向量找文档片段，GraphRAG 找实体间关系链

---

### L5 规划与决策层 (Planning & Decision Layer)

**定位**：系统的大脑——分析目标、制定计划、选择策略、评估风险。

**解决的核心问题**：用户意图到执行路径之间的"怎么干"问题。不是拿到意图就执行，而是先想清楚。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **任务拆解器** | 目标解析器（意图→可执行目标），子任务生成器（目标→步骤列表），依赖关系分析器（步骤间先后/并行关系） | 复杂意图无法一步完成，需要拆成可执行的子任务序列 |
| **执行计划生成器** | 计划模板加载器（常见场景的预定义计划），执行序列编排器（子任务排序+并行分组），回退计划构建器（每步的失败备选方案） | 不只生成最优路径，还要有Plan B |
| **策略选择器** | 规则策略引擎（确定性场景走规则），LLM 规划策略（开放场景走 ReAct/CoT），策略优先级仲裁器（规则优先→LLM兜底） | 不同场景需要不同的"思考方式"——简单走规则快而准，复杂走LLM灵活 |
| **规则校验器** | 前置条件检查器（执行前必须满足的条件），业务口径校验器（数据/参数的合规性），边界约束验证器（金额上限/权限范围） | 从原L2迁入——校验是决策的一部分，不是理解的一部分 |
| **风险评估器** | 业务风险检测器（敏感操作/大额交易），权限风险扫描器（越权/提权检测），操作影响评估器（不可逆操作评估） | 高风险操作必须先评估再执行，不能"先斩后奏" |

**关键设计点**：
- 规则校验器从L2迁入，因为校验是"决定能不能做"，不是"理解说了什么"
- 策略选择器的规则优先→LLM兜底是性能与灵活性的平衡
- 风险评估器是触发HITL的关键——高风险操作自动升级为人审

---

### L6 工具与动作执行层 (Tool & Action Layer)

**定位**：干活的层——调用工具、执行动作、返回结果，并保障可靠性。

**解决的核心问题**：规划层决定"做什么"之后，这层确保"做得对、做得稳"。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **工具注册中心** | 工具发现器（自动扫描注册），工具元数据管理器（入参/出参/权限/描述），工具版本控制器（多版本共存与灰度） | Agent 能用哪些工具、每个工具怎么用，需要统一管理 |
| **调用编排器** | 参数填充器（从上下文中提取参数填入工具入参），调用序列调度器（串行/并行/条件分支），并行调用管理器 | 多工具协同调用——先查A再调B，或同时调C和D |
| **结果标准化器** | 响应格式适配器（不同工具的返回格式统一化），错误码映射器（工具错误→业务错误），空值/异常处理器 | 工具返回五花八门，需要统一成上层能理解的结构 |
| **可靠性保障器** | 重试管理器（指数退避/自定义重试策略），幂等处理器（幂等键生成与去重），补偿事务协调器（Saga模式多工具回滚） | 生产环境必备：网络抖动要重试、写操作要幂等、多步操作要可回滚 |
| **熔断降级器** | 超时监控器，失败计数器，熔断状态机（Closed→Open→Half-Open），降级策略执行器（缓存/默认值/简化流程） | 某个工具挂了不能拖垮整个系统 |
| **MCP 协议适配器** | MCP 客户端，工具描述转换器（MCP Tool Schema → 内部工具元数据），双向通信管理器 | 通过 MCP 协议标准化工具接入，解耦工具提供方与消费方 |

**关键设计点**：
- 可靠性保障器是新增模块——重试、幂等、补偿事务是企业级必备
- MCP 适配器使工具接入标准化，新工具只需实现 MCP 协议即可
- 熔断与重试协同：熔断管"还要不要调"，重试管"调一次不成再调几次"

---

### L7 多 Agent 与 Skill 编排层 (Orchestration Layer)

**定位**：多 Agent 协作与 Skill 动态加载的编排层。

**解决的核心问题**：单个 Agent 能力有限——复杂任务需要多个专业 Agent 协作，Skill 是 Agent 能力的增量扩展机制。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **Agent 注册中心** | Agent 元数据存储（能力描述/适用场景/SLA），能力目录管理器（按领域/技能分类），健康状态监控器（心跳/可用性） | 有哪些 Agent、各自擅长什么、现在能不能用 |
| **任务路由器** | 意图-Agent 匹配器（意图→最合适的Agent），负载均衡器（同能力多实例分流），优先级调度器（紧急任务优先） | 任务派给谁——找最合适的Agent，不是随便找 |
| **协作协调器** | 多 Agent 会话管理器（共享上下文），任务分片器（大任务拆分给多Agent），中间结果交换器（Agent间数据传递） | 多Agent并行或串行协作时的协调 |
| **结果聚合器** | 多源结果合并器，冲突消解器（不同Agent结果矛盾时的仲裁），最终输出合成器 | 多个Agent各自返回结果，需要合并成连贯的最终答案 |
| **Skill 加载器** | Skill 解析器（Markdown/YAML 格式），Skill 依赖解析器（前置Skill/工具依赖），热加载管理器（运行时动态增删Skill） | Skill 是Agent的"技能包"——按需加载、动态扩展 |

**关键设计点**：
- 路由器的意图-Agent匹配依赖L2的意图识别结果
- Skill 的热加载意味着不停机即可扩展Agent能力
- 结果聚合中的冲突消解是企业场景的特殊需求——两个Agent给出矛盾答案时怎么裁决

## 4. 横切模块详细设计

---

### M1 反思与学习引擎 (Reflection & Learning Engine)

**定位**：系统的自进化能力——从交互中学习，持续优化。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **交互日志采集器** | 全链路追踪（请求→理解→规划→执行→响应），意图决策记录器，工具调用记录器 | 没有数据就无法学习，全链路日志是进化的原材料 |
| **失败模式分析器** | 意图误识别检测器，槽位提取失败分析器，工具调用失败归因器 | 定位"哪里做得不好"才能针对性改进 |
| **知识进化器** | 新词发现器（用户用了但词库里没有的术语），同义关系验证器，本体同步更新器 | 企业的术语和知识是动态变化的，系统要跟上 |
| **模型微调触发器** | 数据标注管道，训练集构建器，模型评估与部署器 | 当规则和提示词不够用时，触发模型微调 |
| **A/B 测试框架** | 实验分组器，指标对比分析器，优胜策略自动切换器 | 改了之后到底变好了没？用数据说话 |

---

### M2 安全与治理层 (Safety & Governance Layer)

**定位**：系统的安全护栏——防止有害输入/输出、保护隐私、管控权限、审计追溯。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **输入过滤器** | 敏感词检测器，Prompt 注入防护器，输入长度限制器 | 恶意输入是Agent系统的头号攻击面 |
| **输出审核器** | 有害内容分类器，幻觉检测器，输出一致性校验器（与知识源交叉验证） | Agent 不能乱说——说错话在企业场景代价很大 |
| **PII 脱敏器** | 实体识别器（手机号/身份证/银行卡/邮箱），脱敏策略引擎（掩码/替换/哈希），授权场景下的脱敏恢复 | 企业数据合规，敏感信息不能明文出现在日志或LLM上下文中 |
| **权限校验器** | RBAC 角色解析器，工具级权限检查器（谁能调什么工具），数据范围过滤器（行级/列级数据权限） | 不同角色不同权限——实习生不能审批百万合同 |
| **审计追踪器** | 操作日志记录器（谁在什么时候对谁做了什么），合规报告生成器，异常行为告警器 | 出了事要能追溯，合规审计需要完整记录 |

---

### M3 基础设施横切层 (Infrastructure Cross-cutting Layer)

**定位**：生产级运行的基础设施保障——可观测、成本可控、流量可控、租户隔离。

| 子模块 | 职责 | 解决什么问题 |
|--------|------|-------------|
| **可观测性 (Observability)** | Metrics 采集（延迟/吞吐/错误率），分布式 Tracing（跨层请求追踪），Alerting（异常自动告警） | 系统运行状况透明——哪里慢了、哪里错了、需要关注什么 |
| **Token 成本管控** | 调用配额管理（按用户/部门/场景），成本归因（每次对话花了多少钱），预算超限熔断 | LLM 调用是按 token 计费的，不控成本会爆预算 |
| **限流 (Rate Limiting)** | 每用户 QPS 限制，每渠道并发限制，全局吞吐上限 | 防止突发流量打垮系统，防止个别用户独占资源 |
| **多租户隔离** | 租户级配置隔离（模型/提示词/工具），资源配额隔离，数据沙箱 | 企业内部按部门/业务线隔离，互不干扰 |
| **用户反馈闭环** | 反馈采集器（点赞/点采/纠正/补充），反馈标注管道（高质量反馈→训练数据），效果追踪器（改进后对比） | 没有反馈就没有进化——M1学习引擎的数据源头 |

## 5. 层间数据流

```
用户输入
  │
  ▼
┌─────────────────────────────────┐
│ L1 交互呈现层                    │  渠道适配 → 消息标准化
│   ↓ 传递标准化消息               │
├─────────────────────────────────┤
│ L2 语义理解层                    │  NLU 管线：意图 + 槽位
│   ↓ 输出 Intent + Slots         │
├─────────────────────────────────┤
│ L3 上下文状态层                  │  状态查询/更新，槽位补全
│   ↓ 输出完整上下文               │
├─────────────────────────────────┤
│ L4 记忆与知识层                  │  知识检索 + 记忆注入
│   ↓ 附挂知识与记忆               │
├─────────────────────────────────┤
│ L5 规划与决策层                  │  生成执行计划 + 风险评估
│   ↓ 输出 Execution Plan         │
├─────────────────────────────────┤
│ L6 工具与动作执行层              │  调用工具 → 返回结果
│   ↓ 输出 Action Results         │
├─────────────────────────────────┤
│ L1 交互呈现层（回程）            │  渲染响应 → 返回用户
└─────────────────────────────────┘

横切层 M1/M2/M3 在每层均有切面介入
```

## 6. MVP 裁剪指南

| 优先级 | 必选层 | 说明 |
|--------|--------|------|
| **P0** | L1 + L2 + L3 + L6 | 最小可用：能对话、能理解、能记住、能执行 |
| **P1** | + L4 + M2 | 加知识检索和安全护栏，可上生产 |
| **P2** | + L5 + M3 | 加规划决策和基础设施，可规模化 |
| **P3** | + L7 + M1 | 加多Agent编排和自进化，完整形态 |
